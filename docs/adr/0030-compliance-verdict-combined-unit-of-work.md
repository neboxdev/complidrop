# 0030. Compliance verdict commits in the same transaction as its inputs (combined unit of work)

- **Status:** accepted
- **Date:** 2026-06-22
- **Deciders:** Ruben G. (founder), Claude (implementing #337)

## Context

The persisted compliance verdict (`Document.ComplianceStatus` + the `ComplianceCheck` rows) was written in a transaction **separate** from the canonical compliance inputs it is derived from (`Document.ExtractionFields` + the typed `GeneralLiabilityLimit / EffectiveDate / ExpirationDate` columns), with no concurrency token on `Document` and no lock spanning the verdict read→write. Both input-writing paths persisted inputs and verdict as two transactions:

- **Manual edit** (`DocumentEndpoints.UpdateFields`, also `UpdateDocument` for vendor/type): committed inputs (`SaveChanges`), then called `ComplianceCheckService.EvaluateAsync`, which did its OWN read→compute→`SaveChanges` of the verdict.
- **Extraction** (`ExtractionWorker.PersistSuccess`): committed inputs + `ComplianceStatus = Pending`, then called `EvaluateForSystemAsync` (same separate read→compute→save).
- The shared core `EvaluateInternalAsync` was a plain `FirstOrDefaultAsync → ComputeOutcome → SaveChangesAsync` — no `FOR UPDATE`, no version token. The two callers used different DbContexts (`AppDbContext` vs `SystemDbContext`), so there was no shared change tracker to reconcile them.

**The reachable race** (found by the #235 hunt — concurrency audit #243 §6, filed as #337): a user edits a document's fields *while* a (re)extraction of the same document is in flight. The worker computes verdict(W) from freshly-extracted inputs W; the user commits inputs U and verdict(U); the worker commits verdict(W) **last**. Terminal state: **inputs = U but `ComplianceStatus` = verdict(W)** — a verdict that contradicts the stored inputs. It does not self-heal (the hourly `ComplianceSweepBackgroundService` only flips date-driven Expired/ExpiringSoon transitions, never re-runs rule evaluation), and the detail page renders the stored verdict beside the edited field values — so a user can see **Compliant next to a deficient GL limit** (the dangerous direction for a compliance product). This is *not* the ADR 0017 "re-extraction overwrites manual edits by design" contract, which yields a clean last-writer-wins (fully W or fully U); this is a torn pair that is neither.

The compliance/audit core is a #246 "touch only with a control-asserting test + AuditLog golden snapshot" area, which is why this is its own `/start` ticket.

## Decision

**Fold the verdict computation into each input-writer's own unit of work (combined unit of work).**

A new `IComplianceCheckService.ApplyEvaluationAsync(DbContext context, Document doc, CancellationToken ct)` evaluates an **already-tracked** document and applies the verdict (`ComplianceStatus` + the `ComplianceCheck` rows) to the **same context WITHOUT saving**. The input-writing paths call it just before their own `SaveChanges`, so the inputs and the verdict they imply commit in **one transaction**:

- `UpdateFields` / `UpdateDocument`: apply the verdict on the edited tracked entity, then `SaveChanges` once.
- `ExtractionWorker.PersistSuccess`: apply the verdict on the freshly-extracted tracked entity, then `SaveChanges` once (the separate `EvaluateForSystemAsync` pass is removed; the worker no longer parks the doc at `Pending` for a second transaction to resolve).

Each writer now commits the **whole `(inputs, verdict)` tuple atomically**, so any interleave resolves to one writer's consistent pair — never a mix. This is **last-writer-wins on the tuple**, which is exactly the ADR 0017 contract (re-extraction overwriting a manual edit is by design); the fix is that it's now applied to the inputs *and* the verdict together instead of leaving them independently racing.

`EvaluateAsync` / `EvaluateForSystemAsync` are retained for the **pure re-grade callers** that do not themselves change inputs (the "Check again" button, the vendor/checklist/rule-change fan-outs) — they now delegate to `ApplyEvaluationAsync` and add the `SaveChanges`. Their read→compute→write window is a single in-method round-trip with no interleaved input-write from the same action, so they are not the scoped race; folding the verdict into the input-writers is what closes it.

**Best-effort preserved via Pending-degradation.** The pre-existing, deliberately-tested guarantee — a failing inline recompute must not fail the user's edit (`ThrowingComplianceCheckService` tests) — is kept: if `ApplyEvaluationAsync` itself throws, the caller catches it, sets `ComplianceStatus = Pending` (a safe "not yet graded" state the sweep / "Check again" resolves), and commits the inputs. So the edit still succeeds, but the stored verdict is never a **confident value computed from now-stale inputs** — `Pending` is non-committal, not contradictory. The worker does the same (matching its prior best-effort `try/catch`) rather than failing the extraction into a costly re-OCR/LLM retry. `ApplyEvaluationAsync` performs all its I/O (template load, existing-checks load) *before* any change-tracker mutation, so a throw leaves no partial check rows for the fallback `SaveChanges` to commit.

## Consequences

### Positive
- **No torn `(inputs, verdict)` pair** under any manual-edit-vs-(re)extraction interleave — the acceptance invariant. Proven by a deterministic two-context interleave test and an AuditLog golden snapshot.
- **One audit row per logical edit.** The interceptor now emits a single `document.updated` row whose Before/After spans the input change *and* the verdict transition, instead of two rows from two transactions (the first of which captured a torn new-inputs/stale-verdict snapshot).
- **The worker no longer publishes an intermediate `Pending`** between extraction and grading — a processed document reaches its real verdict atomically.
- **No schema change, no entity-wide concurrency token**, so every other `Document` write path (upload, patch, verify, delete) keeps its simple last-writer-wins semantics.

### Negative
- **Best-effort now degrades the verdict to `Pending` on a recompute failure** rather than leaving the previous verdict untouched. This is the correct trade-off (a stale confident verdict is the bug), and the failure is rare — `ApplyEvaluationAsync`'s only I/O is a cheap template load, so a failure ≈ the inputs `SaveChanges` failing anyway.
- **`ComplianceCheck` display rows can still transiently desync** under a concurrent edit-vs-extraction interleave (each writer's `ClearExistingChecks` reads the other's not-yet-committed rows), so the detail-page explainer may show mixed check rows — including BOTH writers' sets for the same rules, since each cleared what it could see and inserted its own. The headline `ComplianceStatus` verdict stays consistent with the inputs beside it, and the desync clears on the document's next evaluation, which rewrites the whole set — "self-heals" meaning the next Check-again / edit / rule change / re-extract, since nothing SCHEDULES an evaluation (the sweep does date transitions only). Audit #243 §6 scoped it as cosmetic; making the check rows airtight would need the heavier row-lock / token this ADR deliberately avoids. **DISPLAY is the scope of this bullet, and that is a claim about the read sites, not a hope** — see Amendment 4's *"Display desync" is the whole scope*: the one read site that turned these rows into a NUMBER an auditor relies on (ADR 0048's `RequirementsChecked` CSV column) counts distinct rules, so no artifact ever states the duplicate as a fact about the evidence.
- **"Cosmetic" was wrong for the WORKER, and that is corrected here rather than left in place** (#468, Amendment 4). The clear MATERIALIZES the existing rows and stages a `RemoveRange`, so EF emits a per-row DELETE keyed on the primary key and requires each to affect exactly one row. A competing re-grade that COMMITS inside the window has already deleted precisely those rows, so the DELETE matches nothing and EF raises `DbUpdateConcurrencyException` — out of `ExtractionWorker.PersistSuccess`, whose catch re-saves on the SAME context and throws again, so `FailedAttempts` never increments and the document is zombie-reclaimed every five minutes **re-paying Document AI + the LLM**. A display desync and the money-burning loop this ADR's Option A is refuted over are not the same consequence, and the bullet above described only the first. Amendment 4 makes the check-row DELETE row-count-tolerant; the mixed-set desync above is what remains.

### Neutral
- `ApplyEvaluationAsync` loads `Vendor → ComplianceTemplate → Rules` via the tracked navigation query against the document's *current* (possibly just-edited) `VendorId`, honoring the Vendor soft-delete filter exactly as the prior `Include` did. The pure re-grade path does one extra cheap query (doc, then vendor chain) versus the old single Include — negligible, and not on a hot path.
- `EvaluateForSystemAsync` is now **caller-less in production** — the worker (its only former caller) folds grading into `PersistSuccess` via `ApplyEvaluationAsync`. It is retained as the symmetric system-context entry point to `EvaluateAsync` (and is still exercised by the sample-grading test as a convenient driver); a future system-context re-grade would use it. If no such caller materializes it can be dropped along with the service's now-`EvaluateForSystemAsync`-only `SystemDbContext` dependency.

## Alternatives considered

### Option A — `xmin` optimistic-concurrency token on `Document`
Add a rowversion token so a verdict write that raced an inputs change fails `DbUpdateConcurrencyException` and retries against the fresh inputs. **Rejected** as the primary mechanism: an entity-level token forces **every** `Document` write path (upload, patch, verify, fields, worker persist) to handle the concurrency exception, broadly changing their semantics from last-writer-wins to conflict-and-retry — a large, risky surface for a narrow race. The combined unit of work achieves consistency without it. (A future need for genuine *lost-update prevention*, not just consistency, could revisit this.)

### Option B — `FOR UPDATE` row lock across the verdict read→write
Lock the `Document` row from inputs-read to verdict-write so concurrent writers serialize. **Rejected**: requires every input-writer and re-grade to take an explicit transaction + row lock, more invasive than co-locating the verdict in the writer's existing `SaveChanges`, for the same consistency outcome.

### Option C — Keep best-effort by leaving the prior verdict on recompute failure
On `ApplyEvaluationAsync` failure, commit the inputs and leave `ComplianceStatus` unchanged. **Rejected**: if the edit changed compliance-relevant inputs, the untouched prior verdict is exactly the torn (stale) state #337 is about. Degrading to `Pending` (non-committal) is the safe failure mode.

### Option D — Extraction-status guard on `UpdateFields` (reject edits while Pending/Processing)
Forbid manual edits during an in-flight (re)extraction. **Rejected** as unnecessary friction: ADR 0017 already defines re-extraction-overwrites-edit as intended last-writer-wins, and the combined unit of work makes that outcome consistent, so there is no torn state to forbid the edit over.

## Amendment 1 (2026-08-01) — the two PARTIAL writers must DETECT a conflicting concurrent commit

The combined unit of work holds for **whole-tuple** writers, with one named exception — and the exception is a mechanism, not a column. `ExtractionWorker.PersistSuccess` writes every canonical input it EXTRACTS plus the verdict, so between two such writers whichever commits last wins the whole tuple and the terminal row is somebody's consistent pair. The Decision above is unchanged for them.

**The worker's STALE-BASIS grading is the exception, and this amendment does not close it.** (Amendment 2 does — read this paragraph as the statement of the problem, not of the current behaviour. The mechanism it describes is exactly what Amendment 2 fixes, and the two "obvious" fixes it refutes at the end are still refuted.) `ExtractionWorker.ProcessDocumentAsync` loads the document, spends the whole OCR + LLM run (tens of seconds to minutes) holding that tracked snapshot, and only then does `PersistSuccess` grade through `ApplyEvaluationAsync` and save. EF writes back only the properties the worker MODIFIED, so the exposure is not one column but a mechanism: **every canonical verdict input the worker grades from that minutes-old snapshot and leaves unmodified in its change tracker** keeps whatever a request committed in the window, beside a verdict computed from the pre-run value. Do not read the instances below as the closed list — they are the ones this ticket's analysis reached, and the test for a new one is the mechanism, not the enumeration:

- **`VendorId`** — always. The worker never assigns it, and `ApplyEvaluationAsync` resolves the checklist off the **tracked** FK (`context.Entry(doc).Reference(d => d.Vendor)`), i.e. the vendor as it stood before the run. An `UpdateDocument` PATCH inside that window commits `VendorId = V2` (cleanly, under this amendment's guard); the worker's later `SaveChanges` then writes a `ComplianceStatus` and `ComplianceCheck` rows graded against **V1's** checklist while leaving V2 in the column.
- **`DocumentType`** — whenever `CanonicalDocumentTypes.NormalizeExtracted` yields the value already stored: a blank or absent model answer (which deliberately falls back to the stored type — see ADR 0045) or a canonical answer equal to what the worker read minutes earlier. The assignment runs but changes nothing, so EF omits the column exactly as it omits `VendorId`. The type decides WHICH rules apply (`ComplianceCheckService`'s ordinal `r.DocumentType == doc.DocumentType` filter), so the row keeps the user's re-typed value beside a verdict and check rows graded against the old one. Reachable from the UI: the detail page's `DocumentTypeSelect` is disabled only while its own mutation is in flight, not while the document is processing.
- **Any typed column** (`ExpirationDate` / `EffectiveDate` / `GeneralLiabilityLimit`) whose field the model OMITTED — `CanonicalDocumentFields.ApplyToTypedColumn` runs only for fields the response returned, so an omitted one keeps the stale tracked value and is likewise not written.

Same terminal state in every case — the row holds one value, the verdict beside it was computed from another — and nothing heals it. That is scenario B's terminal state exactly, reached from the other side. **So this amendment closes the request-path half of scenario B and leaves the worker half open** — tracked as [#460](https://github.com/neboxdev/complidrop/issues/460), whose scope is this mechanism, not `VendorId` alone.

Two things that look like the fix and are not, recorded so the follow-up does not re-derive them. Widening this guard to the worker is refuted below (*Why not the `xmin` token*): the cost of an exception out of that `SaveChanges` is a re-paid Document AI + LLM run. And the naive re-read — read the input's current value and assign it onto the tracked entity before grading — makes EF mark that property **modified**, so the worker starts WRITING a column it does not write today: a request landing between the re-read and the commit is then silently clobbered, a lost update traded for the stale-basis one. A workable shape uses the fresh value to DECIDE THE GRADING ONLY (e.g. an explicit vendor-id parameter on the grading path, leaving the tracked FK untouched), which narrows the window from minutes to the gap between that read and the commit but does not remove it — closing it needs conflict DETECTION on the worker's commit that does not cost a re-extraction.

`UpdateFields` and `UpdateDocument` are **partial** writers, and for them one transaction is not enough. Each rebuilds the ENTIRE `ExtractionFields` JSON mirror from its own read snapshot, but EF's modified-property tracking writes back only the typed columns / FK **that request touched**. `Document` carried no concurrency token and nothing locked the row across load → save, so two overlapping edits committed a row that was not either writer's snapshot:

- **Two field edits, different fields (#366 scenario A).** A corrects `general_liability_limit` 1M → 3M and commits (typed column + mirror + verdict). B, loaded before that, edits `certificate_holder`, rebuilds the whole mirror from its stale snapshot (GL still 1M) and grades from its stale tracked entity. B's UPDATE carries the mirror and `ComplianceStatus` but NOT `GeneralLiabilityLimit`. Terminal row: typed column 3M, mirror 1M, verdict computed from 1M. The two copies of one canonical input disagree and the verdict matches neither — and when A's correction was DOWNWARD, the badge reads Compliant beside a deficient displayed limit, the direction #337 exists to prevent.
- **Vendor patch vs field edit (#366 scenario B), the sharper one.** `UpdateDocument` commits `VendorId = V2`; the in-flight `UpdateFields` grades against its stale tracked `V1` and commits that verdict without touching `VendorId`. The row keeps the new vendor with the **old vendor's checklist verdict** — a wrong persisted compliance verdict, which this project's severity anchors call a blocker.

Neither self-heals: `ComplianceSweepBackgroundService` only does date transitions, never rule evaluation.

**Decision.** Those two writers — and only those two — run their load → mutate → evaluate → `SaveChanges` inside a `REPEATABLE READ` transaction (`Endpoints/DocumentWriteConcurrency.RunAsync`). Postgres then refuses to let an UPDATE land on a row version committed after the transaction's snapshot and raises `40001 serialization_failure`, which is exactly the fact these writers need and could not otherwise observe. On that signal the whole callback is **re-run against a fresh read**: new transaction, new snapshot, re-read the document, re-apply the request to it, recompute the verdict. The winner's committed change becomes an INPUT to the retried verdict instead of something the loser half-overwrites. Bounded at `Services/DocumentConcurrency.MaxAttempts` (3).

**A DATABASE-level recompute failure now aborts the unit of work too.** The Decision above promises that a failing inline recompute degrades the verdict to `Pending` and still commits the user's edit. On these two writers that promise now holds only for a recompute failure that is NOT a server-side database error. `EvaluateIntoUnitOfWorkAsync` still catches the throw and sets `Pending` — but if the throw came from Postgres (a statement timeout inside `ApplyEvaluationAsync`'s vendor/rules or existing-checks SELECT, a lock timeout, an out-of-memory), the enclosing transaction is already ABORTED, so the `SaveChanges` meant to carry (inputs, `Pending`) fails with `25P02 current transaction is aborted` and the request 500s having committed nothing. That is deliberate in the same way exhaustion is: the whole unit of work is abandonable, so rolling back leaves the last successful writer's consistent tuple, and nothing torn is ever persisted. `DocumentConcurrency.IsConcurrentUpdateConflict` deliberately does NOT match `25P02` — retrying a transaction Postgres has already aborted fixes nothing — and opening a SECOND transaction to force the `Pending` commit would BE the half-applied write this amendment removes. It is recorded because the guarantee is now CONDITIONAL and nothing else says so: the pinned `ThrowingComplianceCheckService` throws without touching the database, so no test discriminates the two failure kinds.

**Exhaustion answers `409 document.concurrent_update` and commits nothing.** This is stronger than — not a departure from — the Pending-degradation rule above. That rule governs a RECOMPUTE failure, where the user's inputs are committing regardless and the only question is which verdict rides along, so a non-committal `Pending` beats a confident verdict from stale inputs. Here the whole unit of work is still abandonable: rolling back leaves the last successful writer's consistent `(inputs, verdict)` tuple exactly as it stood. Committing the edit with `Pending` instead would BE a half-applied partial write of the shape this amendment removes.

"Commits nothing" has to cover the AUDIT trail as well as the row, and that is not free: `IAuditLogger` writes on its own `SystemDbContext` connection, so a `document.fields_edited` row emitted for an abandoned attempt is outside the rollback's reach. `RunAsync` therefore takes a required `onAttemptAbandoned` and invokes it in the same `catch` that clears the change tracker, so ONE abandonment discards both the entity state and whatever the caller kept outside it — `UpdateFields` uses it to un-say its "an attempt wrote a field edit" fact; `UpdateDocument` passes `null` because it keeps nothing outside its callback (its audit row is staged by the interceptor on the same context, inside the transaction). Resetting that fact at the START of each attempt instead only looks equivalent: `RunAsync` wraps `CommitAsync` in the same conflict `catch` as the write, so the LAST attempt can set it and be abandoned with no next attempt to clear it — and it would make the guarantee a property of WHERE Postgres reports the conflict (`REPEATABLE READ` reports first-updater-wins at the UPDATE; SSI under `SERIALIZABLE`, and any future writer taking an explicit row lock, report at COMMIT) rather than of this code.

**Why not the `xmin` token of Option A.** #366 suggested it as the narrowest fix, on the reading that the retry could be confined to these two endpoints and *"leave the other paths' last-writer-wins undisturbed"*. The code refutes that: `UseXminAsConcurrencyToken` is an ENTITY-level mapping, so it makes EVERY tracked `Document` write optimistic whether or not that path handles the exception. The worst landing is the extraction worker, whose window between claim and `PersistSuccess` is the whole OCR + LLM run (minutes), and whose own remarks (`ExtractionWorker.Clamp`) record what an exception out of that `SaveChanges` costs: the catch's bookkeeping save runs on the SAME context and throws again, `FailedAttempts` never increments, and the document is zombie-reclaimed every 5 minutes **re-paying Document AI + the LLM on every doomed run**. The exact ordinary sequence Option A's rejection worried about — a user correcting fields while an extraction is in flight — would have become a money-burning loop. So Option A's original reasoning stands, and its parenthetical (*"a future need for genuine lost-update prevention could revisit this"*) is answered by scoping the detection to the two writers that need it rather than by taking the token.

**Why not the `FOR UPDATE` of Option B.** It would also serialize the two writers, but it takes the `Documents` row lock BEFORE the transaction touches `ComplianceChecks`, while every other writer's EF batch acquires them in the opposite order. That is a lock-order inversion the current code does not have — a new deadlock (`40P01`) between an edit and a worker persist, whose worker-side landing is the same re-paid extraction. `REPEATABLE READ` changes no lock acquisition order at all: the same statements, in the same order, with Postgres refusing the stale-basis UPDATE instead of applying it. This is also why `DocumentConcurrency.IsConcurrentUpdateConflict` deliberately does NOT match `40P01`: with no inversion introduced, a deadlock here would be a new bug that must surface loudly rather than be absorbed by a retry.

**Recorded residuals, deliberately not fixed here.** Two — and this is where the analysis for THIS ticket stopped, not a proof that the list is complete. Both are the same family: a writer grading from a snapshot the row has moved on from.

1. *The pure re-grade paths* (`EvaluateAsync` / `EvaluateForSystemAsync` / the fan-outs) keep their read → compute → write window. They write no INPUTS, so they cannot LOSE an update — and that is the only comfort. `EvaluateInternalAsync` is a bare `FirstOrDefaultAsync → ApplyEvaluationAsync → SaveChangesAsync` with no lock, no token and no enclosing transaction, so a "Check again" (`ComplianceEndpoints.RunCheck`) that loaded the document before an `UpdateFields` LOWERED a limit writes its now-stale verdict back afterwards: EF marks only `ComplianceStatus` / `UpdatedAt` modified, so the row keeps the lowered limit with a stored `Compliant` and passing `ComplianceCheck` rows citing values the row no longer holds. That is an AFFIRMATIVE verdict contradicting the stored inputs — the #337 state, in the direction that matters — and it does NOT self-heal: nothing schedules a further evaluation and the sweep never re-runs rule evaluation, so only another manual re-grade clears it. Scoped out because putting the whole fan-out under retry is a different change from the one this ticket is; carried as [#461](https://github.com/neboxdev/complidrop/issues/461). **PARTLY ADDRESSED by Amendment 3** — the SINGLE-document re-grade (`EvaluateAsync`, i.e. `RunCheck`) now takes this amendment's own guard; the BATCHED fan-outs still keep the window, and Amendment 3 § What stays open says why that was not one change.
2. *The worker's stale-basis grading* — the mechanism named at the top of this amendment. Its window is the whole extraction run rather than one round trip, and it reaches inputs (1) never touches (the worker writes the tuple; the re-grade writes only the verdict). It is scoped out of this ticket, not judged harmless: closing it changes how the worker grades and needs a mechanism that detects a conflicting commit without re-paying the extraction. [#460](https://github.com/neboxdev/complidrop/issues/460). **ADDRESSED by Amendment 2** — which takes the "fresh value decides the grading only" shape this paragraph gestures at rather than the conflict DETECTION it asks for, so the window shrinks from the whole extraction run to one round trip and residual 2 becomes a strictly smaller version of residual 1. See Amendment 2 § What stays open.

## Amendment 2 (2026-08-02) — the worker grades the row its own commit will LEAVE

Amendment 1 closed the request-path half of scenario B and left the worker half open as residual 2. This closes the reachable part of it: `ExtractionWorker.PersistSuccess` no longer grades the minutes-old tracked snapshot, it grades a prediction of the row its own `SaveChanges` is about to produce.

**The mechanism is derived from the change tracker, not from a list of columns.** `Services/DocumentGradingBasis.AfterPendingCommitAsync(context, tracked, ct)` reads the document's CURRENT committed row (`EntityEntry.GetDatabaseValuesAsync` — one key lookup) and overlays exactly the properties EF reports as `IsModified` on the tracked entity, materialising a **detached** `Document` via `PropertyValues.ToObject()`. That composition IS the prediction, by construction and without enumerating anything:

- a property this writer MODIFIED will be in the UPDATE, so the basis takes the writer's value;
- a property it did not will be absent from the UPDATE, so the basis takes the row's current committed value — including a value a request wrote after the writer's snapshot.

The prediction is bounded to what the WRITER sets, and one property falls outside it: `AuditSaveChangesInterceptor` re-stamps `UpdatedAt` from `SavingChanges`, i.e. after the basis has been materialised, so the basis holds the caller's value and the row commits the interceptor's later one. Immaterial (no verdict input is interceptor-set) and deliberately not chased — the helper predicts what the writer writes, it does not model the pipeline.

All three instances Amendment 1 named fall out of that one rule — `VendorId` (never assigned), `DocumentType` (assigned, but a blank/absent answer falls back to the stored type per ADR 0045 and a canonical answer can equal what was read), any typed column whose field the model omitted — and so does the next one, which is the property that made a mechanism worth building instead of three patches. Nothing pins a list; a column added to `Document` tomorrow is covered the day it is added.

**Grading the right row is only half of it — the verdict has to be WRITTEN, and that takes forcing the column.** (Added by #460 review round 2; the first cut of this amendment shipped the basis without it and left the bug reachable one column over.) `ApplyEvaluationAsync` ASSIGNS `doc.ComplianceStatus`, and EF emits only properties whose current value DIFFERS from the minutes-old snapshot — so a freshly-computed verdict that happens to EQUAL what the row held at claim time produces no SET clause at all, while the `ComplianceCheck` rows are rewritten unconditionally and `UpdatedAt` keeps the UPDATE running. One PATCH reaches it: a document on a strict checklist stored `NonCompliant`, reassigned mid-read to a lenient one (whose re-grade commits `Compliant` against the limit the row still holds), extracted at a value that fails even the lenient floor. The recomputed verdict is `NonCompliant` — equal to the pre-run snapshot — so the column is omitted and the row commits the request's `Compliant` beside the lowered limit and this persist's own FAILING check row. Nothing heals it. The degrade-to-`Pending` catch has the identical hole: a `Pending` snapshot swallows the degrade and leaves a competitor's confident verdict standing over inputs the persist just overwrote.

So `ExtractionWorker.ForceVerdictWrite` sets `IsModified` on `ComplianceStatus` after the try/catch, covering both arms. **This is the `SetTrust` / ADR 0052 §2 shape, not Option G below**, and the distinction is the same one the whole amendment turns on: the verdict is the worker's OWN conclusion about the basis it just graded, whereas Option G forces verdict INPUTS a REQUEST owns. Worker-only — the request-path callers run inside Amendment 1's `REPEATABLE READ`, whose entire point is that a stale-basis UPDATE is REFUSED rather than forced.

`IComplianceCheckService` gains an overload, `ApplyEvaluationAsync(context, doc, gradingBasis, ct)`: it grades `gradingBasis` and applies the verdict + `ComplianceCheck` rows onto `doc` and its context exactly as before. Read-only WITH RESPECT TO `doc` — the overload does write the basis's own `Vendor` navigation, loaded `AsNoTracking` off the basis's own FK (same global filters as the tracked navigation query, so a soft-deleted vendor still reads no-template, pinned by `A_vendor_soft_deleted_mid_extraction_grades_as_no_checklist`) — and no basis value is ever copied back.

Two preconditions make that safe, and both are ENFORCED rather than commented, because a caller breaking either would corrupt data instead of failing: the basis must carry the same `Id` as `doc` (the new check rows are stamped from the BASIS while the clear-existing predicate keys on the TRACKED document, so a mismatched pair would insert against one document and delete another's), and it must be DETACHED (assigning an `AsNoTracking` vendor graph onto a TRACKED principal is what EF turns into spurious inserts at the next `DetectChanges`). `DocumentGradingBasis.AfterPendingCommitAsync` satisfies both by construction; the guards exist for the second caller. **That restraint is the decision, not an implementation detail:** the worker still emits precisely the columns it emitted before, so it cannot clobber a concurrent edit. Re-reading an input and ASSIGNING it would mark the property modified and trade the stale-basis bug for a LOST UPDATE — refuted in Amendment 1 and unchanged here. Contrast `ExtractionWorker.SetTrust` (ADR 0052 §2), which deliberately DOES force its column: that value is the worker's own conclusion about the read it just performed, not a verdict input a request owns. Blurring the two in either direction is a defect.

**The request-path callers deliberately keep the tracked-entity overload,** and switching them would be a bug rather than consistency. `UpdateDocument` grades against a `VendorId` it has assigned in memory and not yet committed, so a freshly-read basis would grade the OLD vendor's checklist — the exact state `Assigning_a_vendor_commits_the_verdict_against_the_new_checklist_atomically` pins. And both partial writers already have a strictly stronger answer in Amendment 1's `REPEATABLE READ` + `40001` re-run, which reloads and re-runs the whole callback rather than patching one basis; deriving a basis outside that retry callback would also break their re-runnability rule.

**No new failure path may cost an extraction.** The basis read is one more way grading can fail, so it sits INSIDE `PersistSuccess`'s existing best-effort `try`: a failure degrades the verdict to `Pending` and the inputs still commit, exactly like any other recompute failure, and never throws out of `PersistSuccess` (whose catch re-saves on the same poisoned context — `FailedAttempts` never increments and the document is zombie-reclaimed every five minutes re-paying Document AI + the LLM, per `ExtractionWorker.Clamp`). A `null` basis falls back to grading the tracked entity, i.e. to the pre-#460 behaviour, because a document that is going away is not one to invent a basis for.

That placement is now PINNED, by a test that makes the read itself fail (`A_failing_basis_read_degrades_the_verdict_without_requeuing_the_extraction`, #460 review round 2). It had to be a new mechanism — a test-only `IDbCommandInterceptor` on `SystemDbContext` that faults one `SELECT` before it reaches Postgres — because nothing existing could: the mid-run-DELETE test soft-deletes, which yields a NON-null basis and never makes the read fail, so hoisting the read above the `try` left the whole suite green. A hard delete is not a substitute either, since the persist's own UPDATE would then throw for an unrelated reason.

**Which delete produces that `null` is a fact, not an assumption, and the first draft of this amendment got it wrong.** `EntityEntry.GetDatabaseValuesAsync` issues an `AsNoTracking().IgnoreQueryFilters()` key lookup, so the SOFT delete that every API path performs (the audit interceptor translates `Remove` into `DeletedAt = now`) still returns the row: a document deleted mid-run IS graded, as the row the commit leaves. `null` therefore means the row is GENUINELY gone — a hard delete, which no production path performs — so the fallback is defensive rather than live. Both halves are pinned DIRECTLY, on the helper, by `The_grading_basis_is_null_only_when_the_row_is_genuinely_gone`; the mid-run-delete INTEGRATION test pins the other property (that this read never becomes a new way for the persist to throw, and — since it now also reassigns the vendor before deleting — that the non-null branch is the one a soft delete takes). An integration test cannot see which branch ran from status alone, which is exactly how the original miscite happened.

**What this refines about "last-writer-wins on the whole tuple".** The worker is a whole-tuple writer only for the inputs it EXTRACTS — that qualifier was always true and is what residual 2 was about. The honest statement after this amendment is narrower and sufficient: the terminal row may hold a MIX of the worker's extracted values and a concurrent request's, per column, which is ADR 0017's per-column last-writer-wins contract; the verdict beside them is COMPUTED from whatever mix the row ends up holding **and is then forced into the UPDATE** — both halves are load-bearing, because a computed-but-omitted verdict leaves the row holding a competitor's instead, which is not the invariant. The `ComplianceCheck` display-row transient desync recorded in § Consequences is unchanged.

### What stays open

**The re-read → commit window is NOT closed, and this amendment does not claim it is.** A request committing between `AfterPendingCommitAsync` and the worker's `SaveChanges` puts the row back in the residual-2 state. What changed is the size: from the whole OCR + LLM run (tens of seconds to minutes) to one round trip, which makes it the same shape and roughly the same size as residual 1's read→compute→write window ([#461](https://github.com/neboxdev/complidrop/issues/461)) rather than a category of its own. Closing it needs the COMMIT to detect a conflicting write, and every detecting shape available throws out of a `SaveChanges` whose failure is the money-burning loop above — `xmin` (Option A) and `REPEATABLE READ` (Amendment 1) are both refuted for this writer specifically, and a conditional/guarded verdict UPDATE would have to sit outside the one transaction that makes (inputs, verdict) atomic, which is the thing this ADR exists to prevent. Recorded as still-open rather than closed; if it is ever worth closing it belongs with [#470](https://github.com/neboxdev/complidrop/issues/470) — the batched fan-out's window, which is this family's live ticket now that #461 has shipped, and which is likewise a read→compute→write window whose remedy cannot be `REPEATABLE READ`. (This pointer said "#461" until that ticket closed; a residual whose successor is a closed issue is a residual nobody will find.) **Updated by Amendment 3:** #461 has since closed its half by TAKING the `REPEATABLE READ` guard — which is available to a re-grade precisely because a throw out of ITS `SaveChanges` costs a retry rather than a re-paid extraction. So the two windows are the same shape and are NOT closable the same way, and this one is now the larger of the pair rather than the smaller. It stays with #461's family in kind, not in remedy.

**`ExtractionStatus` + `ExtractionTrust` are still decided from the pre-run snapshot, and this amendment deliberately does not move them.** Twenty lines above the basis read, `PersistSuccess` asks `DocumentFieldReadability.UnreadableCanonicalFields(doc)` — of the tracked entity, not of the row the commit will leave — and its result drives `distrusted`, hence both columns and hence ADR 0042 coverage exclusion. It is the same mechanism this amendment fixes for the verdict, so it has the same reachable shape: a document sitting at `ExpirationDate = null` from a prior ADR 0040 unreadable read, re-extracted while the user types the correct date and saves, with the model returning the same unparseable text. `ApplyToTypedColumn` writes null over a null snapshot, so EF omits the column and the row keeps the user's valid date, but the walk saw a null column beside unparseable raw text and the row commits `ManualRequired` + `Distrusted` — while a read-time `UnreadableCanonicalFields` of that row is EMPTY, so the vendor drops to Action needed and the detail page's `ManualReviewCard` (gated on that list since #459 round 2) names nothing. Fail-CLOSED, pre-existing in mechanism, and `Mark verified` is the exit. NOT swapped onto the basis here on purpose: doing so would redefine trust from "what this extraction produced" to "what the row ends up holding", which contradicts ADR 0052 §2's "the worker's OWN conclusion" and needs its own decision rather than a side effect of this one. Carried as [#467](https://github.com/neboxdev/complidrop/issues/467).

**A concurrent regrade landing in the same window can THROW out of the persist, and § Consequences' "cosmetic" call is too generous.** `ApplyEvaluationAsync` materializes the document's existing `ComplianceCheck` rows and stages a `RemoveRange`; if another writer's regrade deletes exactly those rows before the persist's `SaveChanges`, the DELETE affects 0 rows and EF answers `DbUpdateConcurrencyException` — on this writer that is the re-paid Document AI + LLM landing, not a display desync. The window is one in-method round trip rather than the whole run, and it predates this amendment (it arrived with #337, which put `ApplyEvaluationAsync` inside `PersistSuccess`), but nothing recorded it. Found while constructing the after-the-basis-read interleave, which reproduces it deterministically; carried as [#468](https://github.com/neboxdev/complidrop/issues/468). **CLOSED by Amendment 4** — the DELETE is now row-count-tolerant, which leaves the unit of work exactly where this ADR put it. Note what that does NOT close: the re-read → commit window above is a different residual and stays open.

### Alternatives considered (Amendment 2)

- **Option E — pass an explicit vendor id to the grading path.** The narrowest reading of #460, and what the ticket's own "direction that does work" suggests first. **Rejected as insufficient:** it answers `VendorId` and leaves `DocumentType` and the typed columns to a second and third parameter, which is the enumeration the ticket explicitly asks not to ship. A whole-document basis answers all of them with one seam.
- **Option F — grade the freshly-read row wholesale.** Simply re-read the row and grade THAT. **Rejected as wrong, not merely coarse:** it discards the worker's own extraction, so a re-extraction that LOWERS a limit would be graded against the pre-run value the row is about to lose — a false-affirmative verdict, the #337 direction that matters. Pinned by `The_workers_own_extracted_value_still_decides_the_verdict_where_it_wrote_it`.
- **Option G — force the worker's verdict INPUTS into the UPDATE (the `SetTrust` shape).** Make the worker a genuine whole-tuple writer by setting `IsModified` on every canonical input. **Rejected:** `SetTrust` forces a column whose value is the worker's OWN conclusion; these are inputs a request owns, so forcing them is precisely the lost update Amendment 1 refutes — a user's mid-read vendor reassignment or type correction would be silently overwritten by the value the worker read minutes earlier. Note what this does NOT reject: forcing `ComplianceStatus`, which this amendment now does (`ExtractionWorker.ForceVerdictWrite`, above). Same mechanism, opposite ownership — the verdict is the worker's conclusion, the inputs are the request's facts. Reading Option G as "the worker never forces anything" is the misreading that left the verdict unwritten in the first cut.

## Amendment 3 (2026-08-02) — the single-document PURE re-grade takes Amendment 1's guard

Amendment 1 recorded the pure re-grade window as residual 1 and scoped it out. This closes the reachable half of it. Nothing about the diagnosis changed — residual 1's description is accurate, and it is worth restating that this is NOT the benign self-healing window the first draft of that amendment claimed: `ComplianceSweepBackgroundService` does date transitions only, nothing else schedules an evaluation, so an affirmative verdict left over lowered inputs stands until a human clicks "Check again" a second time.

**`ComplianceEndpoints.RunCheck` runs inside `DocumentWriteConcurrency.RunAsync`** — the same `REPEATABLE READ` + `40001` re-run Amendment 1 gave the two partial writers, with the same bound (`DocumentConcurrency.MaxAttempts`). A conflicting commit inside the window forces a fresh read and a fresh `ComputeOutcome`, so the verdict that lands is the one the row's CURRENT inputs imply, and the `ComplianceCheck` rows cite the values the row actually holds.

**Why the same mechanism and not a lighter one.** The re-grade writes no inputs, so at first sight it wants something weaker than a partial writer's guard. It does not. The signal it needs is exactly the one `REPEATABLE READ` produces — "the row changed after my snapshot" — and every alternative shape was already refuted for this codebase: an `xmin` token is ENTITY-level (Option A, and Amendment 1's *Why not*), `FOR UPDATE` introduces the lock-order inversion Option B rejects, and a conditional `ExecuteUpdateAsync` on the verdict column cannot carry the `ComplianceCheck` rewrite in the same unit of work, which is the atomicity this whole ADR exists for. Reusing the guard also means one 409 envelope, one retry bound, one place where the isolation level is decided.

**Exhaustion commits NOTHING and leaves the previous verdict ALONE** (`409 document.concurrent_update`). This reads like Amendment 1's answer and gets there by a shorter route: there is no half-applied write to roll back, because the re-grade owns no inputs. What makes leaving the row untouched *correct* rather than merely harmless is the combined unit of work itself — every writer that can win this conflict commits its own `(inputs, verdict)` pair, so the row an exhausted re-grade walks away from is already somebody's consistent tuple. Two other answers were considered and are worse:

- **Degrade to `Pending`.** ADR 0030's degrade rule governs a RECOMPUTE FAILURE, where the user's inputs are committing regardless and the only question is which verdict rides along. Here nothing of ours is committing, so a `Pending` write would REPLACE a correct verdict with a non-committal one — through the very write that kept conflicting, and into a state nothing re-grades. Strictly worse information, fail-closed in name only.
- **Answer `200` with the stored status.** The one button whose entire promise is a fresh verdict would report success for a re-check that did not run. On a compliance product that is the overclaim class this repo has a reviewer persona for.

The 409 carries its own copy (`DocumentWriteConcurrency.RegradeConflictMessage`) — same code, same envelope, different wording, because the edit copy's *"make your change again"* names a change this caller never submitted. `RunAsync`'s message parameter is REQUIRED for the reason `onAttemptAbandoned` is: every call site answers the question rather than inheriting a default that is wrong for it.

**The guard lives at the CALL SITE, and that is a decision with a cost this amendment pays for.** `EvaluateInternalAsync` stays a bare read → compute → write. Putting the transaction inside `ComplianceCheckService` would mean `Services/` owning transaction scope (nothing in that layer does; `Endpoints/` owns it everywhere), would need `Endpoints/DocumentWriteConcurrency` from `Services/` — the wrong direction — and would attach the guard to a method the batched fan-out deliberately does not use. The cost is that a SECOND caller of `EvaluateAsync` re-opens this window somewhere new, silently, with every behavioural test green. So `Adr0030EnforcementTests` pins both halves mechanically: `EvaluateAsync` has exactly ONE production call site, and `RunCheck` invokes it INSIDE the retryable callback (hoisted above the guard, the answer is computed once on the losing snapshot and merely re-served, which no count-only pin can see).

**Re-runnability holds by construction,** which is the property Amendment 1 names as a finding when it is broken. The callback re-reads the document by id on every attempt — `RunAsync` clears the change tracker first, so the retry is a genuine fresh read — and the response is built from THAT attempt's status. Nothing is captured outside it, and `onAttemptAbandoned` is `null` because nothing is kept outside it either: `RunCheck` makes no `IAuditLogger` call, and the interceptor's `document.updated` row is staged on the same `AppDbContext` inside the transaction, so an abandoned attempt's row rolls back with it.

**No other writer's semantics move.** The extraction worker keeps `READ COMMITTED` last-writer-wins, so no failure path re-pays Document AI or the LLM; `MarkVerified`, the delete and the nightly sweep are untouched, pinned as before by `An_unrelated_document_writer_still_wins_last_without_conflicting`. `REPEATABLE READ` changes no lock ACQUISITION order — the same statements in the same order — so Amendment 1's reasoning about `40P01` carries over unchanged.

**No frontend change, and this is the Amendment 1 case rather than the ADR 0050 Amendment 1 one.** The detail page's `recheck` mutation already surfaces `err.message` through its generic error toast, and nothing the page holds CONTRADICTS the 409 — unlike ADR 0050's re-extract conflict, where the client's last payload asserted the read had finished, so the button stayed enabled and every further click 409'd until a manual reload. A re-grade conflict is transient by nature (the next click almost always wins), so there is no state to invalidate; adding an invalidate-on-409 here while the two partial writers deliberately have none for the same code would be an inconsistency, not a fix.

### What stays open (Amendment 3)

**The BATCHED fan-outs keep the window, and this amendment does not claim otherwise.** `ComplianceCheckService.ReevaluateWhereAsync` — behind `ReevaluateForTemplateAsync`, `ReevaluateForVendorsAsync`, `ReevaluateForTemplateOrDocumentsAsync` and the system seed path — still loads a page, grades it and saves it under `READ COMMITTED`, so an edit committing inside that span leaves its document holding the edited inputs beside a verdict graded from the pre-edit ones. Not swept in, for a reason that is about cost profile rather than principle: a page is up to `DefaultReevaluationPageSize` (200) documents committed as one unit, so ONE conflicting edit anywhere in it would abandon and re-run the WHOLE page up to `MaxAttempts` times and then skip it — forfeiting hundreds of unrelated re-grades where today exactly one document goes stale. These callers also run POST-COMMIT on a background token (`PostCommitRegrade`) with no user to answer 409 to, and they are already best-effort per page. Closing it properly wants per-document granularity, which is the batching #293 introduced to stop a single rule edit becoming thousands of serial round-trips. Recorded as still-open and TICKETED — [#470](https://github.com/neboxdev/complidrop/issues/470), whose first obligation is to measure the population before choosing a shape (and whose honest outcome may be "accepted, keep the record"). It carries the `bug` label like every sibling residual of this ADR, because a `bug` issue is what indexes a latent defect into the rolling epic [#48](https://github.com/neboxdev/complidrop/issues/48) (ADR 0006); a residual recorded in prose alone is one nothing sweeps up.

**`EvaluateForSystemAsync` is unguarded and caller-less in production.** It carries the same bare window, and the tenant guard does not transfer as-is (`DocumentWriteConcurrency` takes an `AppDbContext`). A future production caller owes the same question; the interface's own remarks say so.

**The re-grade can still throw where #468 says it can.** A competing writer that deletes the `ComplianceCheck` rows this evaluation has staged for removal makes the DELETE affect 0 rows. On this path that surfaces as `40001` under `REPEATABLE READ` (a retry, which is the point) rather than the `DbUpdateConcurrencyException` #468 describes on the worker — so this amendment narrows #468's blast radius on the request side without closing #468 itself, whose subject is the extraction persist. **#468 has since closed (Amendment 4)**, and it did not change this path: `REPEATABLE READ` still reports the conflict as `40001` at the statement, which is an error rather than a zero-row result, so nothing here is suppressed and the re-run is still what answers it.

### Alternatives considered (Amendment 3)

- **Option H — leave the previous verdict and answer `200`.** The ticket floats "retry, then leave the previous verdict alone" as possibly better than a 409. Half of it shipped: the verdict IS left alone. The other half — reporting success — is rejected above.
- **Option I — degrade the verdict to `Pending` on exhaustion.** Rejected above. Note the asymmetry with Amendment 1: there, degrading is right for a recompute FAILURE because the inputs commit regardless; here nothing commits, so the degrade has no companion write to be non-committal *about*.
- **Option J — put the transaction inside `ComplianceCheckService.EvaluateInternalAsync`.** It would cover any future caller automatically, which is the one thing the shipped shape does not. Rejected on layering (transaction scope belongs to `Endpoints/`, and `Services/` must not reach into `Endpoints/DocumentWriteConcurrency`) and on blast radius (`EvaluateInternalAsync` is shared with the system-context path, which has no `AppDbContext`). The gap it would have covered is covered instead by `Adr0030EnforcementTests`' call-site pin.
- **Option K — extend the guard to the batched fan-outs in the same change.** Rejected on the cost profile in § What stays open, and because it would make one concurrent edit forfeit a whole page of unrelated re-grades — a regression, not a fix.

## Amendment 4 (2026-08-03) — a `ComplianceCheck` DELETE is not row-count-critical

Amendment 2 § What stays open recorded a third way the persist could fail and called § Consequences' "cosmetic" framing too generous. This closes it, and it is the one amendment that changes **nothing** about the unit of work — which is the whole reason it takes this shape rather than a better-looking one.

**The mechanism.** `ApplyEvaluationCoreAsync` clears a document's check rows by MATERIALIZING them and staging a `RemoveRange`, so EF emits one `DELETE … WHERE "Id" = …` per row and requires each to affect exactly one. Every writer that re-grades a document clears the same rows, so one committing between this read and the caller's `SaveChanges` leaves the DELETE matching nothing and EF raises `DbUpdateConcurrencyException`. It has been reachable since #337 put `ApplyEvaluationAsync` inside `PersistSuccess`; nothing recorded it until the #460 after-the-basis-read interleave reproduced it deterministically.

**Why it is the worker's problem specifically.** On a request path the exception is a 500 the user retries, and on the two partial writers and the single-document re-grade it does not even arise (`REPEATABLE READ` reports the conflict as `40001` at the statement, which Amendment 1's re-run answers). On `ExtractionWorker.PersistSuccess` the throw lands in `ProcessDocumentAsync`'s catch, whose bookkeeping `SaveChanges` runs on the SAME context and throws again — so `FailedAttempts` never increments, the document is zombie-reclaimed every five minutes, and every doomed run **re-pays Document AI + the LLM**. That is the same money-burning loop Option A and Amendment 1's *Why not the `xmin` token* are refuted over, reached without any concurrency token at all.

**Decision.** `Data/ComplianceCheckDeleteConcurrencyInterceptor` suppresses the concurrency exception when — and only when — every entry the failure is attributed to is a `ComplianceCheck` being DELETED. A check row is a DERIVED display row: it carries no concurrency token, nothing updates it in place, and every writer that clears it does so in order to replace it. "The row is already gone" is exactly the outcome the DELETE asked for, and no caller reads the affected count. Registered on BOTH `AppDbContext` and `SystemDbContext`, because the rule is a property of the ROW rather than of the caller — the batched fan-outs write check rows through both and keep `READ COMMITTED`, so before this a competing edit forfeited a whole page of unrelated re-grades rather than one document's.

**The guard IS the scope, in both directions a widening could take it.** A check-row UPDATE that matches nothing still throws (nothing updates these rows in place, so a missing row there is real information), and so does a delete of anything else — a `Document`, a `DocumentField`, an INSERT. An entry set EF could not attribute at all keeps the exception too. Suppressing "a delete that matched nothing" generally would hide genuinely lost rows; the persist stages `DocumentField` deletes in the very same `SaveChanges`, so that widening is one line away and is pinned against.

**What this deliberately does NOT do.** It removes the throw, not the interleave. The competing re-grade's own new check rows are already committed when this writer's inserts land, so the document can transiently hold BOTH sets — the display desync § Consequences describes, now the entire residue of this window instead of a thrown persist. It clears on the document's next evaluation. Making the check rows airtight is still the row-lock/token this ADR avoids.

**"Display desync" is the whole scope, and one surface had to be corrected to make that true** (#468 review). § Consequences names the detail-page explainer, where the residue is genuinely cosmetic because the count and the ROWS the reader is looking at are the same thing — the "What we checked" panel lists both writers' rows and the "{n} other requirements met" line counts what it just listed, so they agree with each other and self-heal together. The same rows also fed the [ADR 0048](0048-never-graded-document-asserts-no-affirmative-verdict.md) `RequirementsChecked` CSV column, which is a RAW COUNT with no list beside it in an artifact an auditor relies on — so the residue would have printed "2 requirements checked" against a checklist holding exactly one rule. That is a claim about the EVIDENCE, not a rendering artifact, and it is outside what this section is entitled to accept. `ExportService.CheckCountsAsync` now counts DISTINCT rules, which leaves `DocumentGrading.IsGraded`'s `> 0` threshold — every other consumer of that map, and of `d.ComplianceChecks.Any()` — byte-identical (ADR 0048 §5 records the reasoning at the column). The residue is therefore what this section says it is: a display desync, on the surface that displays the rows.

### Alternatives considered (Amendment 4)

- **Option L — a set-based `ExecuteDeleteAsync` clear.** The obvious "insensitive to the row count" fix, and the ticket's first suggestion. **Rejected as a split unit of work:** `ExecuteDeleteAsync` runs OUTSIDE the change tracker and issues its own statement immediately, joining the caller's transaction only when one is explicitly open. Two callers own none — `ExtractionWorker.PersistSuccess` and `EvaluateForSystemAsync` — so there the clear would COMMIT on its own, separately from the inserts and the verdict. That is precisely the two-transaction shape #337 exists to remove, and it fails in the worse direction: a `SaveChanges` that then fails leaves a document whose checks were deleted and never rewritten. Making it safe would mean requiring an ambient transaction from every caller, which for `EvaluateInternalAsync` means `Services/` owning transaction scope — refuted for its own reasons in Amendment 3 Option J.
- **Option M — give the worker an explicit transaction so Option L's clear could join it.** **Rejected because it re-opens the loop from the other side.** `PersistSuccess`'s grading sits in a best-effort `try` that degrades the verdict to `Pending`; with an explicit transaction open, a DATABASE-level failure in there (a statement timeout in the vendor/rules or existing-checks SELECT, the basis read) aborts the transaction, so the `SaveChanges` meant to carry (inputs, `Pending`) answers `25P02 current transaction is aborted` and throws out of the persist. Amendment 1 records exactly that landing for the two `REPEATABLE READ` writers, where it is correct because a request can 500 and commit nothing; here it costs an extraction. `A_failing_basis_read_degrades_the_verdict_without_requeuing_the_extraction` is what would go red.
- **Option N — catch `DbUpdateConcurrencyException` in `PersistSuccess`, detach the ghost entries, re-save.** The documented EF resolution pattern, and it works. **Rejected as a call-site patch for a property of the ROW:** the identical hazard on the batched fan-out would stay (there it silently forfeits a page of re-grades, so nothing surfaces it), a second caller of `ApplyEvaluationAsync` would have to re-derive the same catch, and the re-save re-runs `SavingChanges` on a context that has already staged its interceptor rows. The interceptor states the rule once, for every writer, and needs no retry at all.
- **Option O — a unique index on `(DocumentId, ComplianceRuleId)` so the mixed set cannot happen.** **Rejected:** it converts the residue into a `23505` out of the persist — the money-burning loop again, from a third direction — and duplicate rows are reachable on plain single-writer paths anyway, the same reasoning ADR 0050 records for the `DocumentField` index it declines.
- **Option P — `REPEATABLE READ` or an `xmin` token on the worker so the conflict is detected instead of tolerated.** Unchanged from Option A and Amendment 1: every detecting shape throws out of the `SaveChanges` whose failure IS the cost being avoided.
